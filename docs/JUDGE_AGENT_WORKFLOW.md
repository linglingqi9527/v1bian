# JudgeAgent 工作流设计

更新时间：2026-08-23

本文件记录 JudgeAgent 的第一版产品与技术工作流。当前阶段先默认处理“已经带发言者标注的文字材料”，暂不把音视频转写、说话人分离、真实模型调用一次性做完。后续所有 Judge 功能开发应先对齐本文件，避免把 Agent 做成普通聊天框。

## 一、产品目标

JudgeAgent 的目标不是简单回答问题，而是把辩论材料转化为一份可解释、可追溯、可训练复盘的评判报告。

它需要同时服务三个场景：

- 看比赛：帮助用户理解一场比赛的胜负、核心交锋和关键判准。
- 写赛评：从当前比赛上下文中生成赛评辅助材料。
- 做训练：根据用户训练记录或比赛材料给出针对性改进建议。

第一版重点先做“评判报告生成链路”，报告内容在网站内可视化预览，导出下载时优先生成类似参考 PDF 的裁判报告格式。网站内的图表、目录、状态和交互只作为阅读与操作层，不必完整进入导出文件。

## 二、输入来源

### 1. Judge 页面直接导入

用户在 Judge 页面上传材料。第一版优先支持：

- `.txt`
- `.md`
- `.docx`
- `.pdf`

当前默认材料已经包含发言者标注，例如：

```text
正一 02:46
感谢主席大家好……

反一 06:11
谢谢主席……
```

### 2. 从写赛评页面呼出

用户在写赛评页面点击 Judge 时，默认分析当前比赛。

后续流程是：

```text
当前比赛
-> 读取比赛 URL
-> 提取视频音频
-> 转写成文字
-> 只保留文字材料进入 JudgeAgent
```

这个来源的优势是：项目里的比赛数据已经有正反方、辩手、比赛 URL、赛评草稿等上下文。即使转写文本里角色不完整，也可以用现有比赛元数据辅助识别一二三四辩。

第一版先保留接口，不在前端实时请求 B 站，也不在 React 页面里直接跑转写。

## 三、标准化文本格式

进入模型前，所有材料都应被整理为统一结构：

```text
辩题：
比赛：
正方：
反方：
材料来源：
角色标注可信度：

[00:02:46] 正一：……
[00:06:11] 反一：……
[00:09:51] 反四：……
```

处理规则：

- 如果材料已有明确角色标签，优先使用原标签。
- 如果角色标签混乱，必须声明“角色标签存在混乱，以下按发言功能处理”。
- 如果没有角色标签，第一版不强行猜测辩手身份，只使用 `SPEAKER_00` 这类临时标签，并要求用户后续校准。
- 如果从写赛评页进入，可以用比赛元数据辅助映射角色，但推断结果必须标注为“由上下文推断”。

## 四、Agent 总流程

JudgeAgent 采用两段式工作流：先建立事实底稿，再生成裁判报告。

```text
输入文件 / 页面上下文
-> 判断文件来源
-> 提取文字
-> 标准化发言文本
-> Extract Facts
-> Judge
-> 输出结构化 JSON
-> 生成内置 Markdown 预览
-> 渲染网站内可视化报告
-> 可选择导出 PDF
```

## 五、Extract Facts

模型不得直接开始写最终报告，必须先抽取事实底稿。

事实底稿字段：

```json
{
  "topic": "",
  "match": "",
  "affirmative": "",
  "negative": "",
  "speaker_map": [],
  "speech_order": [],
  "main_arguments": [],
  "key_clashes": [],
  "uncertainties": []
}
```

事实底稿只允许包含材料中可以确认的内容。

如果材料缺失，必须写入 `uncertainties`，不得补编。

## 六、Judge Skill 内容框架

最终评判报告采用固定框架。

### 1. 开篇材料边界说明

报告开头必须先用一小段说明材料边界，但不要为它单独设置标题。

- 只依据本次上传材料、页面上下文和工具结果判断。
- 若有明确角色标签，则按角色标签处理。
- 若角色标签混乱，则按场上功能处理。
- 若材料不完整，则降低判断强度。

### 2. 本场核心判准

先定义裁判到底在比什么，而不是直接复述比赛。

需要回答：

- 本题真正的比较对象是什么？
- 双方各自需要证明什么？
- 裁判采用什么判断标准？
- 哪些常见误区不应成为本场胜负依据？

### 3. 直接给终局判断

报告前部应直接给出胜负结论：

```text
我最终判：正方/反方获胜，胜负幅度为小胜/中胜/大胜。
```

如果材料不足：

```text
基于当前材料，暂无法给出完整胜负判断，只能给出论证倾向分析。
```

但如果材料已经包含完整或基本完整的辩论发言记录，即使存在转录错误、角色标签不稳定、资料链接缺失，也必须给出比较性胜负判断。此时不确定性只能影响置信度和风险说明，不能把终局判断写成“暂不判胜负”。

终局判断可以在 450 字以内，允许简要解释胜负幅度和最核心的胜负原因，但不得提前展开完整攻防分析。

### 4. 主要论述与攻防整理

不按时间流水账整理，而是按关键论述拆分。

每个论述模块包含：

- 完整裁判分析 `analysis`
- 可选内部摘要：正方主张
- 可选内部摘要：反方攻击
- 可选内部摘要：正方回应
- 可选内部摘要：裁判判断
- 可选内部摘要：残留问题

第一版建议控制在 3-5 个主要论述模块。材料特别短时可以减少到 2 个，材料特别完整时最多不超过 6 个。

用户可读展示优先使用 `analysis`，它应是 650-1000 字的连续分析，可以分 2-3 个自然段。正方主张、反方攻击、回应、裁判判断、残留问题这些字段只是内部摘要，不再作为强制展示结构。

`analysis` 必须写出裁判采信链，而不是观点清单：

```text
主张是什么
-> 为什么该主张能进入本场判准
-> 对方如何攻击
-> 回应是否真正解决了攻击
-> 裁判为什么采信或不采信
-> 这对胜负权重产生什么影响
```

禁止只写“某方提出 A，另一方提出 B，因此某方占优”。如果说“论证有力”，必须解释它完成了哪项证明责任、化解了哪项攻击，或者让对方哪项主张无法进入裁判判准。

### 5. 终局判决

最后重新收束胜负理由，通常给出三条核心原因：

- 谁的判准更稳定
- 谁的核心机制被打穿或保住
- 谁的价值收束更贴合辩题

每条终局理由应控制在 120-220 字，避免重新写一遍完整攻防。

### 6. 本场最佳辩手

主报告不再生成逐个选手复盘，也不逐一给每位辩手建议。主报告只保留“本场最佳辩手”这一项，把省下来的篇幅用于核心判准、主要攻防和终局判决理由。

需要回答：

- 最佳辩手是谁。
- TA 属于哪一方或哪个角色。
- TA 的关键贡献是什么。
- 为什么这项贡献影响了胜负或比赛质量。
- 为什么不是只凭表达流畅度、气势或印象分评选。

如果材料不足，必须写“无法确认”，并说明缺少哪些信息。

最佳辩手部分不应写成“为什么 TA 比其他人打得更好”的横向比较，而应围绕胜局展开叙事：TA 在哪些环节连续完成了什么动作，这些动作如何改变判准、举证责任或攻防压力，最终怎样帮助本方赢下比赛。

### 7. 追问中的选手复盘

用户如果在报告生成后追问某个选手、某个角色或某位辩手的训练建议，例如“正三这场怎么样”“反四有什么问题”“给王欣怡复盘”，JudgeAgent 才进入选手复盘模式。

选手复盘必须包含：

- 这名辩手在本场主要做了什么。
- 优势在哪里。
- 优势为什么成立，如何改变攻防压力、证明责任或判准权重。
- 不足在哪里。
- 不足为什么会影响胜负权重，而不是只说“可以更完整”。
- 下一场最应该改的 1-3 个具体动作。

表达要求：

- 不输出 JSON。
- 不机械列字段名。
- 不使用空话，例如“表达不错”“逻辑更清晰”“加强论证”。
- 每个优点和问题后面都要接原因。
- 若无法确认姓名，按正一、反四、`SPEAKER_00` 等角色回答，并说明置信度。

如果用户问的不是选手复盘，就按普通追问回答，不套用上述结构。

### 8. 不单独生成补充与风险章节

主报告不再单独生成“补充素材库”和“不确定性与材料风险”两个尾部章节。这样做不是缩短报告，而是把篇幅集中给核心判准、主要攻防、终局判决理由和最佳辩手。

处理规则：

- `missing_materials` 和 `uncertainties` 可以保留为空数组，用于兼容旧数据结构。
- 如果确有关键材料风险，只能嵌入开篇材料边界说明或对应攻防段落。
- 如果确有补充素材建议，只能在相关攻防段落中顺带说明，不另开独立章节。
- 不得在 Markdown 中生成“六、补充素材库”“七、不确定性与材料风险”。

## 七、篇幅与重点控制 Skill

JudgeAgent 必须控制报告长度和标题层级。它可以在主要分析部分写得充分，但前置说明必须短，不能无限扩写。

### 1. 默认字数预算

第一版默认输出：

- 简版：2400-2800 字，适合弹窗快速预览。
- 标准版：5600-6500 字，适合 Judge 页面阅读。
- 完整版：7800-9000 字，适合导出 PDF。

如果用户没有指定，默认使用标准版。

首次生成报告时必须尽量写到当前模式上限附近。删除选手复盘、补充素材库和风险章节后，省下来的字数必须分配给主要论述与攻防、终局判决理由和最佳辩手，不得导致报告整体变短。

### 2. 模块篇幅预算

标准版采用模块级硬预算：

- 开篇材料边界说明：60-120 字。只交代依据、角色处理方式和材料风险，不单独设置标题，不展开分析。
- 本场核心判准：320-520 字。定义比较标准、双方证明责任和判准为何决定胜负，不复述大量攻防。
- 终局判断：360-560 字。必须尽早给结论，说明谁赢、赢在哪里、胜负幅度为何成立，但不提前写完整攻防。
- 主要论述与攻防：每个模块 `analysis` 1000-1500 字，整体 3-5 个模块。这里是必须展开的主体部分。
- 终局判决理由：3 条，每条 300-480 字。只做收束，但要讲清判准、机制、攻防结果之间的推导关系。
- 本场最佳辩手：280-460 字。说明人选、方别、关键贡献和评选理由。

简版应优先压缩“主要论述与攻防”，保留完整的开篇材料边界说明和终局判断。

完整版可以扩展“主要论述与攻防”“终局判决理由”和“最佳辩手”，但前置三段仍必须维持短篇幅。

如果超出预算，优先压缩例子复述、铺垫性解释和重复价值抒情，不压缩裁判判断、证据引用和裁判采信链。

### 3. 标题层级约束

Markdown 输出只允许使用两级标题：

```markdown
# 标题
## 一级模块
### 二级模块
```

标题结构必须固定为：

```markdown
# Judge 评判报告

以下判读只依据本次上传材料……如果角色标签混乱，以下按场上功能处理。

## 一、本场核心判准
## 二、终局判断
## 三、主要论述与攻防整理
### 论述一：……
### 论述二：……
### 论述三：……
## 四、终局判决理由
## 五、本场最佳辩手
```

不得新增同级大标题。不得使用四级及以下标题。不得把普通段落写成标题。

主要论述的小标题必须使用 `论述一/论述二/论述三` 这种序号结构，并且标题应概括交锋主题，不得写成情绪化标题。

### 4. 标题字数限制

- 主标题不超过 18 字。
- 一级模块标题不超过 14 字。
- 主要论述小标题不超过 28 字。
- 标题不得出现完整判断理由，理由放在正文里。

### 5. 必须加粗的重点

Markdown 输出中必须加粗：

- 胜负结论，例如：`**正方获胜**`。
- 胜负幅度，例如：`**小胜到中胜之间**`。
- 核心判准中的关键词。
- 每个主要论述模块的最终裁判判断。
- 本场最佳辩手。
- 所有“不确定”“材料不足”“由上下文推断”等风险提示。

### 6. 禁止滥用加粗

不得整段加粗。不得把每句话都加粗。

每个自然段最多加粗 1-2 个关键短语。加粗内容应是裁判心证、核心概念、风险提示或行动建议，而不是普通修饰词。

### 7. 段落密度

报告应保持可读：

- 前置三段单段建议 60-140 字。
- 主要分析单段建议 120-220 字。
- 超过 260 字必须拆段。
- 不连续堆叠超过 4 个长段。
- 列表项应短而具体。
- 证据引用应短摘录，不复制大段原文。

## 八、反幻觉控制 Skill

JudgeAgent 的核心约束是：

```text
先建立事实底稿，再基于证据裁决；所有推断必须标注不确定性，所有判断必须回链到材料。
```

### 1. 输入边界约束

模型只能依据：

- 用户上传材料
- 系统传入的比赛元数据
- 工具返回结果
- 用户显式补充信息

不得自行补充：

- 辩手姓名
- 队伍身份
- 赛制规则
- 比赛结果
- 外部案例
- 外部论文

如果材料中没有出现，必须标记为“未在材料中确认”。

### 2. 先事实，后判断

Step 1: Extract Facts

- 辩题
- 正反方
- 辩手/角色
- 发言顺序
- 核心论点
- 关键交锋
- 不确定信息

Step 2: Judge

- 只能基于 Step 1 中已经抽取的事实做裁决。
- 如果事实底稿中没有证据，不得给强判断。

### 3. 强制证据引用

每一个关键胜负判断都要绑定证据。

```json
{
  "claim": "反方现状激活机制被正方拆掉",
  "judgment": "正方略占上风",
  "evidence_refs": [
    {
      "speaker": "正方三辩",
      "time": "00:32:10",
      "quote": "为什么你有刺激我没有刺激"
    }
  ]
}
```

如果没有证据，只能写：

```text
材料不足，无法确认。
```

公开报告中不展示时间戳。证据表达优先写成“正三追问……”“反四回应……”，不要输出 `03:41`、`17:24/18:07` 这类定位数字。时间戳只作为内部定位辅助，不进入用户可读报告。

### 4. 推断必须降级

以下内容必须标注为推断：

- 根据发言顺序判断某人是一辩/二辩
- 根据比赛环节判断发言功能
- 根据上下文补齐队伍信息
- 根据材料片段判断胜负倾向

推断不能写成事实。

### 5. 输出前自检

最终输出前必须检查：

- 每个胜负理由是否有证据引用？
- 是否把推断和事实分开？
- 是否把外部补充资料和场上内容分开？
- 是否存在没有材料支撑的辩手评价？
- 是否把痛苦、遗憾、价值判断、胜负标准混为一谈？
- 是否承认了材料缺失和角色标签混乱？

## 十、网站内可视化

网站内可视化只服务阅读和操作，不要求和下载 PDF 完全一致。

第一版可视化模块：

- 顶部目录：按比赛/报告查看结果。
- Markdown 预览：展示完整评判报告。
- 关键交锋卡片：展示论述、攻防、裁判判断。
- 证据引用：展示对应发言者、时间点、短摘录。
- 后续追问：按用户问题展示选手复盘或论点解释。
- 后续追问：按用户问题展示选手复盘、论点解释或素材补强。

这些模块可以逐步做，不影响最终报告导出。

## 十一、导出下载

- A4 页面。

- 先声明材料边界。
- 再给核心判准和终局判断。
- 中段按主要论述/攻防展开。

## 十三、模型接口策略

前端不直接绑定某一个模型。

建议统一为：

```text
VITE_JUDGE_LLM_PROVIDER=mock | ollama | api-proxy
```

第一阶段：

- `mock`：用于前端开发和流程验证。
- `ollama`：用于本地免费演示，适合 Mac/Windows 切换，不需要云端 API Key。
- `api-proxy`：用于后续接千问、OpenAI 或其他云模型；浏览器只请求自己的代理服务，不直接持有模型 API Key。

模型返回必须通过结构化 Schema 校验后才能进入报告渲染。

正式给用户使用时应采用 `api-proxy`。浏览器只请求本项目的 `/api/judge-agent`，API Key 保存在服务端环境变量中。当前开发期通过轻量 Node 代理实现：

```bash
npm run judge:api
npm run dev
```

云模型代理采用 OpenAI-compatible `/chat/completions` 格式，默认适配阿里云 DashScope 兼容模式，也可以通过环境变量切换到 DeepSeek、OpenAI 或其他兼容服务。

服务端 `.env.local` 示例：

```text
JUDGE_AGENT_PORT=8787
JUDGE_AGENT_HOST=127.0.0.1
JUDGE_LLM_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
JUDGE_LLM_API_KEY=替换为你的云模型 API Key
JUDGE_LLM_MODEL=qwen-plus
JUDGE_LLM_FAST_MODEL=qwen-turbo
JUDGE_LLM_TEMPERATURE=0.2
JUDGE_LLM_JSON_MODE=false
```

前端模型选择不直接展示厂商名，而是展示体验档位：

- `高`：走 `JUDGE_LLM_MODEL`，用于正式报告。
- `快`：走 `JUDGE_LLM_FAST_MODEL`，用于快速试跑。
- `本地`：走 Ollama 本地模型，不消耗云模型额度，主要用于开发兜底和离线演示。

当前前端可识别的配置：

```text
VITE_JUDGE_MODEL_PROFILE=default
VITE_JUDGE_LLM_PROVIDER=api-proxy
VITE_JUDGE_AGENT_ENDPOINT=/api/judge-agent
VITE_JUDGE_OLLAMA_ENDPOINT=http://localhost:11434/v1/chat/completions
VITE_JUDGE_OLLAMA_MODEL=qwen3:4b
```

安全边界：

- 不得把 DashScope / OpenAI API Key 写入 `VITE_` 环境变量。
- 云模型必须走 `api-proxy`，由后端或本地代理持有 API Key。
- 如果 provider 未配置或配置错误，前端应回退 `mock` 或显示明确错误。

## 十四、第一版开发顺序

1. 固化本工作流文档。
2. 建立 JudgeAgent service 接口，但内部仍使用 mock。
3. 建立文件读取与标准化接口。
4. 建立 JSON Schema 与校验函数。
5. 将 mock 输出渲染成内置 Markdown。
6. 在网站内做基础可视化报告。
7. 建立 PDF 导出接口。
8. 再接真实模型 provider。
9. 最后再处理音视频转写和说话人分离。
